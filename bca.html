// Why you study what you study — the mental model

Language First, Not Framework

Companies don't test frameworks — they test thinking. Python is the language that gets out of your way so your brain can focus on solving problems, not syntax. Once you own Python, you can pick up any language in weeks.

DSA is How Computers Think

Every program, every app, every AI model is built on Arrays, Trees, Graphs and the algorithms that walk through them. Understanding DSA means understanding how to make software fast and correct — the two things interviewers test.

System Design is How Companies Think

Building a feature is engineering. Building something that serves 10 million users reliably is system design. Senior companies care about this because software fails at scale — and they need people who understand why.

Practice > Passive Learning

Reading code doesn't teach you to code. Watching a lecture doesn't make you solve problems. The only way to learn is to build something, break it, debug it, and fix it. Every topic in this plan has deliberate practice built in.

Spaced Repetition is Not Optional

Your brain forgets 70% of what you learn in 24 hours without review. Spaced repetition — reviewing at Day 1, Day 3, Day 7, Day 30 — is how you move knowledge from short-term to permanent memory. This is not a hack; it's neuroscience.

Show Don't Tell — Build Projects

When you walk into an interview, a GitHub full of projects is worth more than a certificate. Projects prove you can apply knowledge, handle ambiguity, and ship real things. Every phase ends with a project.

Python — The Language of Thinking

Months 1–5 · 20 weeks · ~3 hours/day
Why Python first? Python is the closest programming language to English. It lets you focus on logic, not semicolons or memory management. Every top product company accepts Python in interviews. And Python powers AI/ML — so you're investing in a skill with a 10-year shelf life.
🧠 How to Study Each Python Topic
01
Watch First (30 min)

Watch the linked YouTube video. Don't code yet. Just understand the concept mentally.

02
Read + Annotate (30 min)

Read the official docs or linked blog. Write 3 lines in your own words: "This topic does X, which is useful when Y."

03
Code From Scratch (60 min)

Close all tabs. Open a blank file. Write the examples from memory. Make them break. Fix them.

Data Structures & Algorithms — The Interview Language

Months 5–14 · 36 weeks · 2 hrs learning + 2 hrs problems/day
Why DSA? Because every product company — Google, Amazon, Flipkart, Zomato, CRED — tests your ability to solve algorithmic problems. These aren't trick questions. They test whether you can think about efficiency: given 1 billion users, how do you find a name in 10ms? That's DSA.
🧩 The UMPIRE Method for Solving Any DSA Problem
U
Understand

Read the problem 3 times. Ask: what's the input? What's the output? What are the edge cases?

M
Match

Which data structure does this look like? Array? Tree? Graph? Which algorithm pattern — sliding window, BFS, DP?

P
Plan

Write pseudocode. Trace through your example on paper. Never write code before a plan.

I
Implement

Write clean, commented code. Focus on correctness first, then optimize.

R
Review

Test with your own cases, edge cases, empty inputs. Walk through line by line.

E
Evaluate

What's the Time Complexity (Big-O)? Space Complexity? Can you do better?

  • 2D DP: Longest Common Subsequence, Edit Distance
  • Knapsack problem — 0/1 and unbounded
  • Coin Change — the canonical DP problem

System Design — How Engineers Think at Scale

Months 15–20 · 24 weeks · 2 hrs theory + 1 hr design practice/day
Why System Design? Because companies don't just want programmers — they want engineers who can reason about scale. "Design a URL shortener" or "Design WhatsApp" — these questions test whether you understand databases, caching, load balancing, and tradeoffs. Even for entry-level roles, knowing SD basics makes you stand out massively.
🏗️ The System Design Interview Framework (Use Every Time)
1
Clarify Requirements

Functional (what it does) vs Non-functional (scale, availability, latency). Ask: How many users? Read-heavy or write-heavy?

2
Estimate Scale

Back-of-envelope math: QPS, storage, bandwidth. "1M users × 10 requests/day = 100 requests/second." Say this out loud.

3
High Level Design

Draw the architecture: clients, load balancer, servers, DB, cache. Name each component and explain why it's there.

4
Deep Dive

Interviewer picks one component to go deep. Be ready to explain DB schema, API design, caching strategy in detail.

5
Discuss Tradeoffs

No design is perfect. "I chose SQL because of ACID but at 10B rows we'd shard." Show you know the tradeoffs.
