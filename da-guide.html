1 · SELECT, WHERE, ORDER BY, LIMIT, DISTINCT
Foundation — write these without hesitation
Easy
›
SELECT — choose columns. WHERE — filter rows (runs before GROUP BY). ORDER BY col DESC — sort descending. LIMIT n — first n rows only. DISTINCT — unique values.
SELECT name, dept, salary FROM employees
WHERE dept = 'Sales' AND salary > 50000
ORDER BY salary DESC LIMIT 10;
💡
LIMIT without ORDER BY returns random rows. Always sort first for "Top N" queries.
01
Get all employees from the 'HR' department ordered by salary descending
WHERE + ORDER BY DESC
02
Top 5 highest paid employees — show only name and salary columns
SELECT specific cols + ORDER BY + LIMIT 5
03
All unique department names from the employees table
DISTINCT
04
Employees in Sales OR Marketing with salary between 40k and 80k
IN() + BETWEEN + AND
05
All products whose name contains the word "Pro" anywhere
LIKE '%Pro%'

2 · NULL Handling — IS NULL, COALESCE, COUNT trick
Critical for every data cleaning query
Easy
›
NULL = unknown. Never use = NULL. Always IS NULL or IS NOT NULL.
COALESCE(a,b) returns first non-null value.
Interview trick: COUNT(*) - COUNT(col) = number of NULLs in that column.
SELECT * FROM customers WHERE phone IS NULL;
SELECT COALESCE(discount, 0) FROM orders;
SELECT COUNT(*) - COUNT(email) AS missing FROM customers;

3 · GROUP BY + HAVING + Aggregate Functions
SUM, COUNT, AVG, MIN, MAX — most used in reporting
Easy
›
Rule: every column in SELECT must be in GROUP BY or inside an aggregate function.
WHERE filters before grouping. HAVING filters after (use it with aggregates, not raw columns).
SELECT dept, COUNT(*) n, AVG(salary) avg_sal
FROM employees WHERE join_date > '2020-01-01'
GROUP BY dept HAVING AVG(salary) > 50000
ORDER BY avg_sal DESC;

4 · JOINs — INNER, LEFT, SELF + 3-Table Joins
Combining tables — used in 90% of real queries
Medium
›
INNER JOIN — matching rows only. LEFT JOIN — all left rows + matching right (NULL if no match).
Golden pattern: LEFT JOIN + WHERE right.col IS NULL = rows in A but NOT in B.
SELF JOIN — join table to itself with different aliases (hierarchical data).
-- Customers who NEVER ordered
SELECT c.name FROM customers c
LEFT JOIN orders o ON c.id = o.cust_id
WHERE o.order_id IS NULL;

5 · Subqueries + CTEs (WITH clause)
Multi-step query building — makes complex logic readable
Medium
›
Subquery — query inside another. Inner runs first.
CTE (WITH name AS (...)) — named temp result. Makes complex queries readable. Reference like a table.
Correlated subquery — inner query references the outer row. Runs once per outer row.
WITH monthly AS (
  SELECT DATE_FORMAT(dt,'%Y-%m') mo, SUM(amt) rev
  FROM orders GROUP BY 1
)
SELECT mo, rev, LAG(rev) OVER(ORDER BY mo) prev
FROM monthly;

Note: NOT EXISTS is safer when subquery might contain NULLs

6 · Window Functions — ROW_NUMBER, RANK, DENSE_RANK, LAG, LEAD, SUM OVER
Most tested advanced SQL topic in product company interviews
HardMust Know
›
Window functions compute across rows without collapsing them like GROUP BY.
ROW_NUMBER() — unique 1,2,3,4 (no ties). Use for deduplication.
DENSE_RANK() — ties share rank, no gap: 1,2,2,3. Use for Top N per group.
LAG(col,n) — value n rows before. LEAD(col,n) — value n rows after.
SUM/AVG OVER (ROWS BETWEEN ...) — running total, moving average.
-- Top 3 salary per department
WITH r AS (
  SELECT name, dept, salary,
    DENSE_RANK() OVER(PARTITION BY dept ORDER BY salary DESC) rnk
  FROM employees)
SELECT * FROM r WHERE rnk <= 3;
22
Top 3 employees by salary in each department — handle ties correctly
DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC), filter rnk ≤ 3

DAX Measures — SUM, CALCULATE, Time Intelligence
The most important Power BI skill to demonstrate in interviews
HardMust Know
›
Measures are dynamic — they recalculate based on the current filter context from slicers and visuals.
CALCULATE(expression, filter) — evaluates expression with modified filter context. Most powerful DAX function.
DIVIDE(numerator, denominator, 0) — safe division that returns 0 instead of error on divide-by-zero.
TOTALYTD, SAMEPERIODLASTYEAR — time intelligence functions (require Date table). 
Total Revenue = SUM(orders[amount])
Avg Order = DIVIDE([Total Revenue], COUNTROWS(orders), 0)
Revenue LY = CALCULATE([Total Revenue], SAMEPERIODLASTYEAR(dates[date]))
YoY % = DIVIDE([Total Revenue] - [Revenue LY], [Revenue LY], 0)

LOD Expressions — FIXED, INCLUDE, EXCLUDE
Most asked advanced Tableau topic in interviews
HardMust Know
›
LOD = Level of Detail. Computes aggregations at a granularity you specify, independent of the current view.

FIXED — compute at stated dimension only, ignores view filters (except Context).
{ FIXED [Customer ID] : SUM([Sales]) } = total sales per customer, always

INCLUDE — compute at finer grain than the view.
EXCLUDE — compute at coarser grain than the view.
{ EXCLUDE [Region] : SUM([Sales]) } = national total, shown alongside regional breakdown
T09
LOD: total sales per customer regardless of any current view filters
{ FIXED [Customer ID] : SUM([Sales]) }
T10
LOD: each customer's first order date
{ FIXED [Customer ID] : MIN([Order Date]) }
T11
EXCLUDE LOD: show national total sales alongside regional totals in the same view
{ EXCLUDE [Region] : SUM([Sales]) } — add as a reference line or dual axis
T12
Flag "New Customer" vs "Returning Customer" using FIXED LOD for first order date
IF [Order Date] = { FIXED [Customer ID] : MIN([Order Date]) } THEN "New" ELSE "Returning" END

Descriptive Statistics — Mean, Median, Mode, Std Dev, Percentile
Must Know
›
Mean — sum / count. Sensitive to outliers. Use for symmetric distributions.
Median — middle value. Robust to outliers. Always use for salary / income data.
Mode — most frequent value. Use for categories ("most popular product").
Std Deviation — spread around mean. Low = data clustered, High = data spread out.
Percentile — P90 salary = 90% of people earn less than this value.
🎯
Interview: "What's the average salary?" → Always clarify: "Mean or median? For salary, median is more meaningful — a few executives skew the mean significantly."
S01
In SQL: compute mean, min, max, P25, P75, P90 of order amounts in one query
MySQL: use PERCENT_RANK() in a subquery. PostgreSQL has PERCENTILE_CONT directly.
S02
In Excel: AVERAGE, MEDIAN, MODE, STDEV on a salary column — compare mean vs median
🔗
Correlation vs Causation + Confounding Variables
Must Know
›
Correlation — two things move together (-1 to +1).
Causation — one directly causes the other.
Confounding variable — a hidden third variable causing both.

Classic: ice cream sales and drowning both spike in summer. Hot weather (confounder) causes both.
🎯
Interview trap: "Users who get push notifications buy more. Should we send more?" — Wrong. Maybe we sent notifications only to already-engaged users (selection bias). Always ask: what else could explain this?
S03
Identify the confounding variable: "Cities with more hospitals have higher death rates"
Answer: Sicker people travel to cities with hospitals — illness is the confounder
S04
In your Olist project: late delivery correlates with low review scores — explain why this isn't necessarily causation
🧪
A/B Testing — Hypothesis, P-Value, Sample Size
MediumMust Know
›
Steps: Define hypothesis → Calculate required sample size → Run test (random 50/50 split) → Wait long enough → Analyse with p-value → Decide.

P-value < 0.05 = statistically significant = less than 5% chance the result is random noise.
Confidence interval = range where true effect likely falls ("1.2% to 3.4% improvement").

Common mistakes: Stopping too early (peeking problem), sample too small, testing too many things simultaneously, ignoring weekly seasonality.
S05
Write a hypothesis for: "We changed the checkout button from grey to orange"
Format: "Changing X will increase [metric] by approximately Y% because [reason]"
S06
A test ran 3 days, showed p=0.03. Manager says ship it. What concerns would you raise?
Think: sample size too small, novelty effect, day-of-week bias, didn't run a full week

Outliers, Skewness, Distributions
Medium
›
Outlier — data point far from others. Detect with IQR (beyond 1.5× IQR from Q1/Q3) or Z-score (beyond ±3 std dev). Never blindly remove — first understand if it's an error or a real extreme event.

Normal distribution — symmetric bell curve. Mean = Median.
Right-skewed — long tail right. Mean > Median (salary distributions).
Left-skewed — long tail left. Mean < Median.
S09
SQL: find all orders where amount is an outlier using the IQR method
Find Q1 and Q3 using PERCENTILE_CONT (or approximation), compute IQR, flag rows beyond Q3 + 1.5*IQR
S10

Data → Data Analysis → Histogram. Describe: is it normal, right-skewed, or left-skewed?

Interview Scenarios
These questions filter candidates in final rounds. Practice answering them out loud — not just reading them. Saying it out loud reveals gaps that reading hides.
📉
"Revenue dropped 20% last month. How would you investigate?"
Most common product analyst scenario — expected at every company
›
Step 1 — Verify it's real: Check if it's a data pipeline issue, tracking error, or calendar difference (fewer working days last month vs the month before).

Step 2 — Segment the drop: Break by product category, geography, customer segment, channel (app/web/paid/organic). Find where the drop is concentrated.

Step 3 — Check funnel metrics: Did traffic drop? Did conversion rate drop? Did average order value drop? Which one changed most tells you where to focus.

Step 4 — External factors: Competitor launch, platform outage, marketing campaign change, pricing change, macro event (holiday, strike, news event).

Step 5 — Hypothesis + query: "I believe it's X because I see Y in the data. Here's the SQL I'd run to confirm."
🎯
Never answer "I'd look at the data." Show structured decomposition into sub-problems. The interviewer is testing whether you think systematically, not whether you know SQL.
📊
"Walk me through your approach to a new analysis from scratch"
›
1. Understand the business question — what decision does this analysis support?
2. Identify data sources — tables, time range, granularity needed
3. Explore + assess quality — nulls, duplicates, date ranges, outliers
4. Clean and prepare — handle nulls, create derived columns
5. Analyse — aggregate, segment, compare, trend over time
6. Visualise — choose the chart type that best shows the insight
7. Derive insights — what's the story? what's surprising or actionable?
8. Recommend — what should the business do? Quantify impact if possible.
9. Communicate — present at the right level for the audience
🧪
"Design an A/B test for a new checkout page"
›
1. Hypothesis: "Changing the CTA from 'Buy Now' to 'Complete Purchase' will increase checkout conversion rate by ~2% because it sounds less pushy."

2. Metric: Primary = checkout conversion rate. Secondary = revenue per session.

3. Sample size: Need: baseline conversion rate, minimum detectable effect (2%), statistical power (80%). Calculate required sample size before starting.

4. Random split: 50% see A (current), 50% see B (new). Assignment must be random and sticky (same user always sees same version).

5. Duration: At least 1–2 full weeks to capture weekly seasonality patterns.

6. Analysis: Is p-value < 0.05? Is the confidence interval fully above 0%? Only then declare a winner.
💬
"Tell me about a time you found a meaningful insight from data" (STAR method)
›
STAR format:
Situation — "In my Olist project, I was analysing e-commerce customer behaviour."
Task — "I wanted to understand why average review scores were low."
Action — "I wrote SQL joining orders, deliveries, and reviews. I grouped delivery delay into bands (on time, 1–7 days late, 8–30 days, 30+ days) and computed average review score per band."
Result — "I found orders delayed 30+ days received a 1.9 average score vs 4.2 for on-time orders. 60% of delayed orders came from only 3 states. My recommendation: prioritise last-mile logistics improvement in those 3 states — it would improve reviews, reduce complaints, and likely improve retention simultaneously."
🎯
Know your project numbers cold. "Around 40%" is weak. "39.2% of late orders came from São Paulo and Minas Gerais" is strong. Precision builds credibility.
🗣️
"Explain your dashboard to a non-technical manager"
›
Rules for communicating to non-technical stakeholders:

1. Lead with the insight, not the method: "Revenue grew 47% in November" — not "I ran a GROUP BY query."
2. Use plain language: no SQL terms, no "p-value," no "NULL," no "ETL."
3. One clear takeaway per visual — don't put 6 things on one chart.
4. Give business context: "This means we lost approximately 2,000 orders compared to last month."
5. Always end with a recommendation: "Based on this, I suggest we prioritise X."

Practice exercise: Explain your Olist dashboard to a family member who knows nothing about data. If they understand the key insight, you've done it right. If they're confused, your communication needs work — not your analysis.
